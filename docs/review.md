## 3. Major（已修复）

### M1 — 连接测试的事件永远不会被消费

**现象**：轮询仅在点击「开始检索」时启动。单独点击「测试连接」时，工作线程投递的
`LogEvent` / 状态事件会滞留在队列中，界面既不显示结果也不复位状态。

**根因**：轮询的启停条件被错误地绑定到 `self._running`（扫描态），而非「是否存在后台作业」。

**修复**：引入作业计数 `_active_jobs` 与 `_ensure_poll()` / `_begin_job()` / `_end_job()`，
轮询的存活条件改为「存在未完成后台作业」。

**回归用例**：`test_connection_test_events_are_polled`（断言作业已登记、事件被消费、作业结束后不再轮询）。

### M2 — ODBC 驱动优先级倒挂

**现象**：本机同时存在 `ODBC Driver 15 for SQL Server` 与旧版通用 `SQL Server` 驱动时，
优先选中了后者。通用驱动属 SQL Server 2000 时代产物，不支持较新特性。

**根因**：原实现按一张固定候选表顺序匹配，未纳入表中的新版本驱动退化为「命中兜底项」。

**修复**：改为三档位排序（`ODBC Driver N` > `SQL Server Native Client N` > `SQL Server`），
档位优先于版本号，同类取版本号更大者。

**回归用例**：`test_unknown_versioned_driver_picked`、`test_highest_unknown_version_wins`、
`test_odbc_line_beats_native_client_same_version`。

### M3 — 数值输入非数字时导致启动崩溃

**现象**：在「并发线程数」等整数框中填入 `八个` 后点击开始，`int()` 转换抛出 `ValueError`，
事件循环之外未捕获，界面看似无响应。

**修复**：新增 `_integer_problems()` 前置校验（明确报出是哪个字段、当前输入是什么），
取值侧改用 `_as_int()` 安全回退。

**回归用例**：`test_integer_problems_detects_garbage`、`test_integer_problems_allows_empty_port`。

## 5. 已确认合理的设计取舍（不予修改）

1. **取消粒度 = 语句级**。`cancel_event` 在任务边界生效，进行中的单条语句由 `query timeout` 收敛。
   强行中断 TCP 连接代价更高，且单表探测通常秒级返回，该取舍成立。
2. **默认 `WITH (NOLOCK)`**。为「是否存在」这类探测换取业务零阻塞，接受可能的脏读；已提供开关。
3. **字段名过滤走 Python `casefold()`，内容匹配走 SQL 排序规则**。两条路径的大小写折叠
   实现不同（对中文均无影响，对拉丁字母语义一致），已在 `design.md` 显式记录该差异。
4. **界面最多渲染 2000 行**。超出部分只计数，避免 Treeview 在极端命中量下卡死；已有告警提示。
5. **强制显式 `COLLATE`**。牺牲极少量灵活性，换取「忽略大小写」勾选在任意服务器排序规则下行为一致。

## 9. v1.3 追加审查（网格选中 + 弹窗 + 路径迁移）

### 9.1 Major

**M5 —— 类体内生成器表达式看不到同类属性，导致 `ResultTable` 直接不可用**

现象：`src/widgets.py` 中 `DATA_KEYS = tuple(k for k in COLUMN_KEYS if k != SEL_COLUMN)`
在导入后首次访问即抛 `NameError: name 'SEL_COLUMN' is not defined`。

根因：Python 的生成器表达式会创建独立作用域，**类体内的推导式看不到同类的其他属性**
（最外层可迭代对象除外，故 `COLUMN_KEYS` 能解析、`SEL_COLUMN` 不能）。这是语言层面的
作用域陷阱，`compileall` 之类的语法检查无法发现，只有真正执行到才会暴露。

修复：改为按位置切片 `COLUMN_KEYS[1:]`（空白控制列恒为第 0 列），并在注释里写明原因，
防止后来者再写成推导式。

**M6 —— 定时器悬空回调（两处）**

现象：`invalid command name "..._reset_result_hint" / "..._poll" while executing ("after" script)`。

根因有两处，性质相同——**在「手动/重复进入」的路径上没有取消已排队的 `after` 定时器**：

1. `_reset_result_hint()` 直接调用后，之前由 `_set_result_hint()` 排队的复位定时器仍在队列里，
   窗口销毁后触发即报错；
2. `_poll()` 假设自己只由定时器触发，故无条件把 `_after_id` 置空；一旦被直接调用，
   那个已排队的轮询定时器就成了孤儿。

修复：两处都改为「先取消可能的在途定时器，再继续」，并新增 `_cancel_timers()` 与
根窗口 `<Destroy>` 兜底绑定，使**任何销毁路径**都不留下悬空回调。

这类缺陷不会让功能出错，但会在日志里留下噪声，且是资源泄漏的一种；本项目历史上已踩过，
故本次把兜底逻辑做成了统一入口而非逐处补丁。

## 10. v1.4 追加审查（命中数据窗口 + 弹窗合并 + 主窗口减负）

### 10.1 Major

**M7 —— 弹窗内的轮询定时器悬空（`_poll` 第三次复发）**

现象：`invalid command name "..._poll" while executing ("after" script)`，
出现在连接方案弹窗与命中数据窗口上。

根因与 M6 完全同源：`_poll()` 里无条件 `self._after_id = None`，**假设自己只由定时器触发**。
一旦被直接调用（测试、或未来任何手动驱动路径），那个已排队的定时器就没人取消，
窗口销毁后触发即报错。

修复：两个 `_poll` 均改为「先 `_cancel_timer()` 再继续」，与主窗口的处理方式统一。

**这次复发说明了一个工程问题**：同一类缺陷在三处独立出现，靠逐处打补丁会反复漏。
因此本轮把「`after` 回调必须先取消在途定时器」写进了项目约定（见 workspace memory），
并在评审中把它列为新增代码的检查项。

## 11. v1.5 追加审查（文案换行 + 落盘时机 + 按方案记住密码 + 默认值/布局）

### 11.1 缺陷

**M8（第一轮修复后又复发的形态）—— 窗口未映射时 `winfo_width()` 返回 1，导致换行宽度失效**

现象：指示灯文案的换行宽度被设成最小值，长文案仍会把弹窗撑宽。

根因：`ConnectionDialog._center_on()` 在窗口尚未映射时用 `self.form.winfo_width()` 计算
换行列宽，而此时该值恒为 1（实际尺寸要等映射后才确定）。
换成 `winfo_reqwidth()`（内容请求尺寸）后，无论是否已映射都能拿到稳定值。

该问题由新加的界面用例 `test_lamp_text_wraps_inside_window` 捕获——
它断言 `wraplength > 160`，直接暴露了「拿不到宽度就退化」的路径。

**M9 —— `_hint_wrap` 属性在构建期未初始化**

现象：`AttributeError: 'tkapp' object has no attribute '_hint_wrap'`，主窗口直接起不来。

根因：结果提示的 `<Configure>` 绑定在 `_build_body` 中，而 `_hint_wrap` 的初始化写在
`_build_body` 的**末尾**。`<Configure>` 在构建过程中就会触发（子控件被 grid 时），
于是处理器先于初始化执行。

修复：把所有「会被事件回调读取」的状态字段统一前置到 `__init__` 开头初始化。
这是 Tk 事件驱动下的通用注意点——**回调可能在构建期就到达**，不能假设「构建完才有事件」。

## 12. v1.6 追加审查（打包为可执行程序）

### 12.1 Major

**M10 —— `SPECPATH` 语义差异导致打包直接失败**

现象：首次打包报 `script 'D:\Documents\WorkBuddy\main.py' not found`。

根因：spec 里写的是 `ROOT = Path(SPECPATH).resolve().parent`，设想 `SPECPATH` 是 spec 的**文件路径**；
而 PyInstaller 实际传入的是 spec 所在的**目录**。于是 `.parent` 又向上取了一层，解析到项目目录之外。

修复：两种语义都兼容——
`_SPEC_PATH = Path(SPECPATH).resolve()`，再用 `is_file()` 判断后取父目录。
这类问题只能在真实构建时暴露，属于「静态检查覆盖不到」的一类，因此把「必须跑一次 bat\build.bat
并核对产物」写进了验收清单。

**M11 —— `for /f` 中两个带引号的绝对路径取不到输出，版本号静默退化为 0.0.0**

现象：`bat\build.bat` 打包成功，但产物名是 `MssqlFieldFinder-v0.0.0.exe`——版本号没读出来，
而脚本因为兜底默认值没有报错，属于**静默错误**（比直接失败更危险）。

根因：cmd 在 `for /f ('命令')` 中执行命令时会走一遍引号剥离逻辑；
当命令行以引号开头且含两段带引号的路径时，命令被截断，输出为空。

修复：先 `pushd` 到项目目录，再用**相对路径**调用 `python main.py --version`。
实测对比过四种写法，只有「相对路径」与「整串再加一层引号」两种可行，已在脚本注释中记录原因。
